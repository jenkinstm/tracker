# CLAUDE.md

Правила работы над этим проектом. Читай вместе с `docs/spec.md` — там полное ТЗ.

## Что это

Личный веб-трекер питания, тренировок и веса. Один пользователь, self-hosted на VPS,
домен `fit.profkosm.ru`. Подробности, приоритеты и критерии приёмки — в `docs/spec.md`.

Перед началом любого блока работ прочитай:
- `docs/spec.md` — требования (нумерация FR-x.x, на неё ссылаемся в коммитах)
- `docs/context.md` — дефолты профиля, что уже решено и почему
- `docs/roadmap.md` — порядок блоков и что сделано

## Стек

- Монорепозиторий: `apps/web` (фронт), `apps/api` (бэк), `packages/shared` (типы, расчёты)
- Фронт: React 18 + TypeScript + Vite, Tailwind, TanStack Query, Recharts, Dexie, vite-plugin-pwa
- Бэк: Node.js 22 LTS + Fastify + Prisma, Zod для валидации, web-push
- БД: PostgreSQL 16, расширение `pg_trgm`
- Инфраструктура: docker compose (app + db + caddy), деплой через GitHub Actions

Версии не меняем без обсуждения. Новые зависимости — только если без них решение
заметно хуже, и с объяснением зачем.

## Жёсткие правила

1. **Схема БД — только через `prisma migrate`.** Ручной SQL и правки в существующих
   миграциях запрещены. Изменение схемы = новая миграция.
2. **Секреты только в `.env`.** В коде, в коммитах, в примерах — никогда.
   Любое новое значение сначала появляется в `.env.example` с пустым значением.
3. **Расчётные функции живут в `packages/shared` и покрываются тестами.**
   Это тренд веса, темп по регрессии, прогноз даты, сверка TDEE, пересчёт КБЖУ
   на граммы, расчёт BMR/TDEE. Тест обязателен вместе с функцией, не «потом».
   Обязательно проверяй граничные случаи: ноль замеров, один замер, разрывы в датах,
   нулевой и положительный темп, деление на ноль.
4. **КБЖУ в `diary_entries` денормализованы намеренно.** Не «исправляй» это на
   вычисление из `foods` — правка продукта не должна менять историю задним числом.
5. **Валидация на входе API — Zod-схемой.** Типы для фронта выводятся из неё,
   руками не дублируются.
6. **Ничего не выполняй на продовом сервере.** Деплой идёт через CI. Если нужно
   действие на сервере — напиши скрипт и объясни, что он делает.

## Стиль

- Ответы, комментарии и сообщения коммитов — на русском.
- Коммиты: `feat(diary): поиск по локальной базе (FR-2.1)`. Ссылка на FR обязательна,
  когда работа закрывает пункт ТЗ.
- Одна ветка на блок работ, ветки от `main`.
- Интерфейс — русский. Строки в i18n-словаре, не хардкодом в JSX.
- Мобильный интерфейс первичен. Тап-цели ≥ 44 px, числовые поля — `inputMode="decimal"`.
- Комментарии в коде — только там, где неочевидно «почему». «Что» видно из кода.

## Как вести работу

- Один блок — одна сессия — одна ветка. Список блоков в `docs/roadmap.md`.
- Блок заканчивается работающим приложением, а не «половиной модуля».
- Перед крупным блоком покажи план: какие файлы создаются, какие меняются, какие
  миграции добавляются. Дождись подтверждения.
- После завершения блока обнови `docs/roadmap.md` — отметь сделанное.
- Если требование в ТЗ противоречит реальности или невыполнимо в выбранном стеке —
  скажи об этом прямо, не изобретай молча обходной путь.

## Чего не делать

- Не добавлять аналитику, трекеры, внешние CDN. Данные о здоровье, всё остаётся на своём сервере.
- Не расширять функциональность за пределы текущего блока «раз уж я здесь».
- Не собирать фронт на сервере — сборка только в CI (2 ГБ RAM не хватит).
- Не трогать основной домен `profkosm.ru`, работаем только с поддоменом.
