# Внешние API: ключи, лимиты, цены

Все цены проверены в августе 2026. Они меняются — перед закупкой сверься с прайсом провайдера.

> **Область MVP — только Яндекс.** Разделы 1 и 2 (Yandex Search API: Wordstat + позиции) нужны сейчас. Разделы 3–5 (XMLRiver, DataForSEO, Google) — справочные, к вехе M9. В MVP не регистрируйся у посредников и не клади им деньги.

## 1. Wordstat API в составе Yandex Search API v2 (частотность) — основной источник

**Внимание: путь через Яндекс Директ устарел.** Отдельный API Вордстата на `api.wordstat.yandex.net` с OAuth-токеном и заявкой в поддержку Директа больше не выдаётся новым пользователям — официальная страница документации Вордстата редиректит в Yandex Cloud. Wordstat теперь живёт в Search API v2 внутри AI Studio, без зависимости от рекламного аккаунта.

**Авторизация:** заголовок `Authorization: Api-Key <ключ>`, ключ сервисного аккаунта из AI Studio.
**Endpoint root:** `https://searchapi.api.cloud.yandex.net/v2/wordstat/`

**Методы:**

| Метод | Path | Назначение |
|---|---|---|
| GetTop | `/topRequests` | частотность фразы (`totalCount`) + топ похожих (`results`) + ассоциации (`associations`) |
| GetDynamics | `/dynamics` | частотность по периодам (день/неделя/месяц) |
| GetRegionsDistribution | `/regions` | разбивка по регионам с `affinityIndex` |
| GetRegionsTree | `/getRegionsTree` | справочник регионов, дёргаем один раз и кэшируем |

Точная спецификация — в proto-файле `yandex/cloud/searchapi/v2/wordstat_service.proto` в публичном репозитории `yandex-cloud/cloudapi`. Смотри туда, а не в гипертекстовую документацию: в proto нет неоднозначностей.

**Что нужно получить:**
1. Аккаунт AI Studio / Yandex Cloud (обычно уже есть, если пользовался YandexGPT).
2. Сервисному аккаунту назначить роль `search-api.executor` в нужном каталоге. Роли `ai.languageModels.user` недостаточно.
3. API-ключ этого сервисного аккаунта в AI Studio. Значение показывается один раз.
4. `folderId` каталога — из консоли Yandex Cloud или из адресной строки (`/folders/b1g...`).

**Переменные:** `YANDEX_SEARCH_API_KEY`, `YANDEX_CLOUD_FOLDER_ID`

Тот же ключ и тот же `folderId` используются и для поиска (раздел 2), и для Вордстата. Это одна интеграция, а не две.

### Грабли, которые надо заложить в код провайдера

1. **`folderId` обязателен в теле каждого запроса.** Без него `INVALID_ARGUMENT`. Если ID неизвестен — вызови API с заведомо неверным значением, настоящий ID придёт в тексте ошибки.
2. **`count` приходит строкой, а не числом** — protobuf `int64` сериализуется в JSON как string. Всегда `int(...)` перед арифметикой.
3. **`period` требует префикс `PERIOD_`**: `PERIOD_DAILY` / `PERIOD_WEEKLY` / `PERIOD_MONTHLY`. Без префикса — ошибка.
4. **Для `PERIOD_MONTHLY` поле `toDate` обязано быть последним днём месяца**, для weekly — последним днём недели. В proto это не описано, узнаётся только из ответа сервера. Нужна функция `last_day_of_period(date, period)`.
5. **`associations` может отсутствовать** на узких запросах — приходит пустой массив, не `null`.
5а. **`results[0]` — не обязательно запрошенная фраза.** Иногда она первой строкой с частотностью, равной `totalCount`, иногда её в списке нет вовсе. Искать по нормализованному тексту, никогда не брать нулевой индекс.
5б. **Ассоциации шумные.** Проверено 28.08.2026 на «купить окна»: рядом с полезным «стеклопакет» (39 981) пришли «сколько стоят линзы» (3222 — уход в оптику) и «окн» (7727 — обрубок токена). Фильтровать обязательно.
6. **Rate limit** — стандартный для Yandex Cloud, порядка 5–10 rps. Суточного потолка в привычном виде нет: 10 000 фраз собираются за полчаса, а не за 10 дней.

### Чего в API нет по сравнению с веб-интерфейсом

- **Операторы `!слово`, `+слово`, `[слово]`, кавычки — не поддерживаются.** Передать их в `phrase` можно, но точная фразовая частотность не гарантируется.
- Сравнение нескольких фраз в одном вызове — нет, только по одной.
- Разделения на левую и правую колонку в привычном виде — нет.

**Следствие для нашего продукта:** поле `freq_exact` (частотность в кавычках) через этот API получить нельзя. Либо снимаем точную частотность через XMLRiver (раздел 3, он парсит веб-интерфейс со всеми операторами), либо MVP живёт на базовой частотности. Решение — за человеком, см. `OPEN-QUESTIONS.md`.

### Два разных режима вызова, не путать

`numPhrases` не влияет на стоимость запроса, но влияет на смысл операции. Разводим их по разным задачам:

| Задача | `numPhrases` | Что берём | Когда |
|---|---|---|---|
| Сбор частотности по своей семантике | `1` | только `totalCount` | массово, 1 вызов на фразу, по расписанию |
| Расширение семантики | `2000` | `results` + `associations` | по кнопке, точечно, единицы вызовов |

Не собирай ассоциации в фоне на всю семантику: это тысячи мусорных фраз, которые никто не разберёт.

**Фильтрация ассоциаций перед показом:** отсекать частотность ниже порога (по умолчанию 100), отбрасывать фразы без общего корня с исходной (простая проверка по стеммингу — берёт «стеклопакет» для «окна»? нет, не берёт — поэтому порог мягкий, а финальное решение за человеком). Ассоциации никогда не добавляются в проект автоматически: только предложение с чекбоксами.

### Цена

**# VERIFY.** По состоянию на апрель 2026 Wordstat в составе AI Studio Search API был бесплатным: без оплаты шли API-вызовы, платить надо было только за токены LLM-моделей. Официальный прайс Search API описывает тарификацию поисковых запросов (см. раздел 2), но Wordstat как отдельный тип запроса там явно не выделен.

Проверять только фактом: сделать сотню вызовов и посмотреть биллинг в консоли. До подтверждения в расчётах считаем Wordstat бесплатным, но закладываем в `provider_settings` возможность выставить цену.

## 2. Яндекс Search API v2 (позиции в Яндексе) — вариант A

Официальный поисковый API Яндекса, живёт в Yandex Cloud / AI Studio. Единственный полностью легальный способ снимать выдачу Яндекса.

**Цены** (из примера расчёта в официальной документации по тарификации):
- Синхронные запросы (ответ сразу): 250 000 запросов = 122 000 ₽ → **≈ 0,49 ₽ за запрос, ~488 ₽ за 1000**.
- Отложенные запросы (асинхронно, ответ до 5 дней): 50 000 запросов = 1 525 ₽ → **≈ 0,03 ₽ за запрос, ~30 ₽ за 1000**.
- Есть бесплатный тестовый объём для новых аккаунтов (порядка 1 000–10 000 запросов в месяц — уточняется в консоли).

**Как на самом деле работает отложенный режим** (уточнено 28.08.2026):

- Нормативный минимум обработки — **5 минут**. Обычно результат готов ровно через пять минут или на секунды позже: сервис намеренно выдерживает паузу, балансируя нагрузку.
- На больших пулах время растёт. Сотня запросов — те же пять минут. Сто тысяч встанут в очередь и будут обрабатываться волнами, часть пула может ждать полчаса и дольше.
- **Готовый ответ хранится 12 часов, потом удаляется безвозвратно.** Не забрал за это время — заплатил и не получил данные.
- Жёсткого лимита на размер очереди нет. Ограничивает скорость постановки (несколько десятков RPS, дальше `429`) и суточный бюджет каталога: при исчерпании API просто перестаёт принимать задачи.
- Схема стандартная: отправка → `operation_id` → опрос до `done`.

**Вывод для продукта: ежедневное расписание возможно.** Пять минут — это не пять дней, риск снят.

**Но 12 часов хранения — жёсткое архитектурное требование.** Если опрашивальщик лёг на ночь, данные за ночной прогон пропали вместе с деньгами. Требования к M5:
1. Таблица `deferred_operations` со сроком годности каждой операции.
2. Опрос идёт независимо от того, жив ли исходный воркер: отдельная периодическая задача забирает всё, что `pending` и не просрочено.
3. Размер пачки ограничен так, чтобы гарантированно вычерпать её за 12 часов с запасом.
4. Операция, просроченная без забора результата, помечается `expired`, пишется в лог расходов как потраченная впустую и переотправляется.
5. Алерт в Sentry при первой же просроченной операции — это симптом, а не мелочь.

**Вывод: для трекера позиций используем только отложенный режим.** Позиции не нужны в реальном времени, а разница в цене шестнадцатикратная. Архитектурно это значит: задача ставит пачку отложенных запросов, получает `operation_id`, воркер опрашивает их или ловит колбэк.

**Что нужно получить:**
1. Аккаунт в Yandex Cloud, организация, платёжный аккаунт.
2. В консоли включить Search API.
3. Сервисный аккаунт с ролью `search-api.executor` (или `search-api.webSearch.user`).
4. API-ключ этого сервисного аккаунта + `folder_id`.

**Переменные:** `YANDEX_SEARCH_API_KEY`, `YANDEX_CLOUD_FOLDER_ID`

## 3. XMLRiver — веха M9, не для MVP (позиции в Google и Яндексе, резерв по Вордстату) — вариант B, рекомендуемый для старта

Российский посредник, перепродаёт лимиты. Один API для Google, Яндекса и Вордстата — это сильно упрощает MVP: одна интеграция вместо трёх.

**Тарифы (прайс на август 2026), цена за 1000 запросов:**

| Тариф | Предоплата | Google | Яндекс | Wordstat* | Yandex Search API |
|---|---|---|---|---|---|
| Базовый | нет, бессрочный | 25 ₽ | 25 ₽ | 25 ₽ | 28 ₽ |
| Про | 5 000 ₽ / 30 дней | 20 ₽ | 20 ₽ | 20 ₽ | 27 ₽ |
| Мега | 15 000 ₽ / 30 дней | 15 ₽ | 15 ₽ | 15 ₽ | 25 ₽ |
| Гига | 50 000 ₽ / 30 дней | 12 ₽ | 12 ₽ | 12 ₽ | 24 ₽ |

\* цена за 1000 страниц Вордстата; на одной странице — частотность запрашиваемой фразы и до 2000 уточняющих фраз.

Важно: на тарифах Про/Мега/Гига неиспользованные средства сгорают в конце 30 дней. Пока объёмы не стабильны — сиди на Базовом.

**Что нужно получить:** регистрация на xmlriver.com, пополнение баланса. В личном кабинете — `user id` и `key`, они уходят в query-параметрах запроса.

**Переменные:** `XMLRIVER_USER`, `XMLRIVER_KEY`

**# VERIFY:** нужно проверить в личном кабинете, сколько результатов отдаётся за один запрос — ТОП-100 целиком или страницами по 10. Если страницами, стоимость съёма ТОП-100 умножается на 10, и тогда для Яндекса выгоднее прямой Search API в отложенном режиме. Это первое, что надо выяснить перед закупкой; занеси ответ сюда и в `OPEN-QUESTIONS.md`.

## 4. DataForSEO (позиции в Google) — веха M9, не для MVP

Нужен, если клиентам важна выдача Google в других странах, или как резерв к XMLRiver.

- Standard queue (асинхронно, до 45 минут): **$0,0006 за SERP = $0,60 за 1000**
- Priority (~1 минута): $0,0012 за SERP
- Live (~6 секунд): $0,002 за SERP
- Минимальный депозит $50, дальше pay-as-you-go, кредиты не сгорают.
- Единица тарификации — 10 результатов; параметр `depth` увеличивает стоимость за каждые дополнительные 100 результатов. Для Google Organic один SERP содержит до 100 результатов.

**# VERIFY:** реальная списанная сумма за задачу с `depth=100` — проверяется на $1 пробного кредита до того, как закладывать в расчёт.

**Переменные:** `DATAFORSEO_LOGIN`, `DATAFORSEO_PASSWORD` (Basic Auth)

## 5. Google Custom Search JSON API — НЕ использовать

Официальный поиск Google по API: 100 бесплатных запросов в сутки, дальше $5 за 1000 при потолке 10 000 в сутки. Но:
- новым клиентам он больше не выдаётся;
- сервис прекращает работу 1 января 2027 года.

Плюс он и раньше не годился для трекера: отдаёт результаты кастомного поискового движка, а не реальную выдачу google.com, и 10 результатов за запрос ($50 за 1000 проверок ТОП-100).

Не закладывай его в архитектуру даже как fallback.

## 6. Сколько запросов стоит одна проверка позиции

Это главный множитель в смете, и он разный для двух ПС.

| ПС | Результатов за 1 запрос | Запросов на ТОП-100 | Глубина в продукте |
|---|---|---|---|
| Яндекс через Search API | 100 | **1** | 100, фиксированно |
| Яндекс через живой SERP | 10 | 10 | — |
| Google | 10 | **10** | до 100, настраивается |

**Решение 28.08.2026: глубже 100 в Яндексе не идём.** Topvisor допускает 250 на десктопе, но практической ценности в позициях ниже сотой нет, а каждая следующая сотня — это ещё один запрос. Поэтому в Яндексе проверка всегда ровно один запрос, и формула `ceil(depth/100)` для него вырождается в единицу.

Модель подтверждается справкой Topvisor: у них проверка одного запроса в Яндексе включает глубину 100, а в Google — 10, и ТОП-50 в Google стоит впятеро дороже.

**Яндекс:** Search API отдаёт сотню за раз. Живой SERP отдаёт десять — параметр `numdoc`, раньше позволявший брать по 50, Яндекс ограничил летом 2022 именно для борьбы с парсингом.

**Google:** в сентябре 2025 Google отключил параметр `num` — теперь даже с `num=100` возвращается 10 результатов. ТОП-100 в Google стоит десять запросов, и обойти это нельзя.

**Ещё одна оптимизация для Google (веха M9): ранний выход.** Если домен нашёлся в первой десятке, остальные девять страниц парсить незачем. Topvisor реализует это через кешбэк постфактум — нам проще просто не тратить: запрашиваем страницы последовательно и останавливаемся, как только цель найдена. Исключения: когда включено отслеживание конкурентов (нужны их позиции тоже) и когда собирается снимок выдачи (нужна полная глубина). На типичном проекте, где половина фраз в ТОП-20, это режет счёт за Google вдвое.

**Следствие:** глубина проверки — настройка цели (ПС + регион + устройство), а не проекта. По умолчанию 100. Снижение до 50 или 30 режет счёт за Google вдвое или втрое. У Topvisor это тоже настройка, значение по умолчанию — 100.

## 7. Можно ли обойтись без посредников

Разбор по каждому источнику отдельно, потому что ответы разные.

### Яндекс — да, посредник не нужен

Search API v2 — это официальный поисковый API Яндекса, прямой наследник Яндекс XML, закрытого осенью 2023. Топвизор использует для проверок в Яндексе именно его, и в десктопной, и в мобильной выдаче. То есть, работая напрямую с Search API, мы получаем ровно тот же источник данных, что и эталонный сервис.

**Решение: для Яндекса используем Search API напрямую, XMLRiver не нужен.** Отложенный режим, ~30 ₽ за 1000 запросов, один ключ на позиции и Вордстат.

Возражение «в API не настоящая выдача, а ботовыдача» разобрано исследованием Топвизора на 100 тысяч замеров: между API и живым SERP совпадает 7–9 доменов из 10, порядок сайтов в большинстве сессий сохраняется. При этом сам живой SERP при двух одновременных запросах тоже даёт совпадение около 8 из 10. Отдельной API-выдачи не существует.

### Google — официального пути нет вообще

Custom Search JSON API закрывается и настоящую выдачу не отдаёт (раздел 5). Другого официального API у Google нет. Остаётся выбор из двух вариантов, и оба означают парсинг.

**Вариант 1: посредник (XMLRiver, DataForSEO).** 25 ₽ за 1000 запросов на базовом тарифе.

**Вариант 2: свой парсер.** Что придётся построить и содержать:

- пул резидентных или мобильных прокси (дата-центровые IP Google банит быстро);
- решение капч — по оценке Топвизора, 200–300 ₽ за 1000 сложных капч;
- ротацию отпечатков браузера и заголовков;
- парсер разметки выдачи и его починку после каждого редизайна Google;
- очередь с деградацией скорости под капчами.

Арифметика на 100 000 запросов в месяц (это 10 000 фраз × ТОП-100 × 1 съём):

| Статья | Свой парсер | XMLRiver |
|---|---|---|
| Трафик прокси (~0,3 МБ × 100k = 30 ГБ, резидентные $3–7/ГБ) | 9 000–20 000 ₽ | — |
| Капчи | от 2 000 ₽ | — |
| Запросы | — | 2 500 ₽ |
| Поддержка парсера | постоянная | нет |

Свой парсер выходит в 4–8 раз дороже и требует непрерывного обслуживания. Экономия появляется только на очень больших объёмах и при своей инфраструктуре прокси — то есть когда парсинг сам становится бизнесом.

**Про легальность честно:** посредник не делает парсинг Google законным, он переносит операционный риск и техподдержку на чужую сторону. Формально парсинг поисковой выдачи противоречит условиям использования и Google, и Яндекса — на это прямо указывает и сам Топвизор. Разница в том, что у DataForSEO есть договор, юрлицо и SLA, а у самописного парсера на твоём VPS — только твой IP.

**Решение: Google берём через посредника.** DataForSEO, если важна юридическая опрятность и выдача вне РФ; XMLRiver, если важна цена и российская выдача.

### Точная частотность Вордстата — компромисс неизбежен

Официальный API операторы не поддерживает (раздел 1). Варианты:
1. Жить на базовой частотности — бесплатно, но цифры завышены кратно.
2. XMLRiver Wordstat — 25 ₽/1000, операторы работают, но это парсинг веб-интерфейса Вордстата, требующий авторизованных сессий Яндекса.
3. **# VERIFY:** посмотреть, отдаёт ли Яндекс Директ API прогноз показов по фразе с операторами — это официальный путь, но требует рекламного аккаунта, и цифры прогноза не равны цифрам Вордстата.

Ни один вариант не идеален. Вариант 3 стоит проверить до того, как подключать XMLRiver ради одной функции.

## Расчёт стоимости

### Единица учёта

**1 проверка = 1 фраза × 1 поисковая система × 1 съём.** Одна проверка = один запрос к API при условии, что провайдер отдаёт ТОП-100 за раз.

Сбор частотности считается отдельно: 1 фраза = 1 запрос к Вордстату.

### Сценарий А: 10 000 проверок в месяц (буквально по заданию)

| Статья | Расчёт | В месяц |
|---|---|---|
| Частотность, 10 000 фраз | 10 × 100 ₽ (синхронно, дешевле нельзя) | **1 000 ₽** |
| Позиции, 10 000 проверок | 10 × 30 ₽ (отложенный режим) | **300 ₽** |
| VPS (2 vCPU / 4 GB, РФ) | | 800 ₽ |
| Домен | 300 ₽ / год | 25 ₽ |
| **Итого** | | **≈ 2 100 ₽/мес** |

Частотность стоит втрое дороже позиций — это переворачивает интуицию и определяет приоритеты оптимизации.

### Сценарий Б: 10 000 фраз, съём раз в неделю

| Статья | Расчёт | В месяц |
|---|---|---|
| Позиции, 40 000 проверок | 40 × 30 ₽ | 1 200 ₽ |
| Частотность, раз в месяц | 10 × 100 ₽ | 1 000 ₽ |
| VPS | | 800 ₽ |
| **Итого** | | **≈ 3 000 ₽/мес** |

### Сценарий В: 10 000 фраз, ежедневно

| Статья | Расчёт | В месяц |
|---|---|---|
| Позиции, 300 000 проверок | 300 × 30 ₽ | 9 000 ₽ |
| Частотность, раз в месяц | 10 × 100 ₽ | 1 000 ₽ |
| VPS | | 800 ₽ |
| **Итого** | | **≈ 10 800 ₽/мес** |

Те же позиции в синхронном режиме стоили бы 146 400 ₽. Защита в коде: синхронный поиск физически недоступен для пачек больше `SYNC_MAX_KEYWORDS` (по умолчанию 100), проверка на уровне сервиса, а не интерфейса.

### Что добавит Google на вехе M9

Google требует 10 запросов на ТОП-100 против одного у Яндекса. Ориентир: сценарий Б вырастет примерно с 2 000 до 12 000 ₽/мес, сценарий В — с 9 000 до 45 000 ₽/мес. Подробности в разделах 6 и 7.

### Формула для калькулятора в приложении

```
запросов_на_проверку = ceil(глубина / результатов_за_запрос)
    # Яндекс Search API: результатов_за_запрос = 100  -> обычно 1
    # Google (M9):       результатов_за_запрос = 10   -> обычно 10

запросов_в_месяц = Σ по ПС (фразы × съёмов_в_месяц × запросов_на_проверку[ПС])
стоимость_позиций = Σ по ПС (запросов × цена_за_1000[ПС, режим] / 1000)
стоимость_частотности = фраз × сборов_в_месяц × 100 ₽ / 1000
```

Частотность считается отдельной строкой и показывается пользователю отдельно: это разные операции с разной ценой и разной частотой, смешивать их в одну цифру — вводить в заблуждение.

Формулу пишем сразу в общем виде с суммой по ПС, хотя в MVP слагаемое одно. Когда придёт Google, менять калькулятор не придётся: общий множитель по всем ПС занизил бы его в десять раз.

Этот же расчёт показывается пользователю перед запуском съёма и пишется в `api_usage_log` по факту.

### Стоимость разработки

Claude Code работает по подписке Claude (Pro/Max) или по API. Для проекта такого объёма закладывай подписку уровня Max на 1–2 месяца — это дешевле, чем платить за токены по API при интенсивной работе с большой кодовой базой.
