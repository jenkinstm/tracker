# ТЗ: веб-приложение «Трекер питания, тренировок и веса»

Версия 1.0 · 27.07.2026 · решения зафиксированы, можно начинать разработку

---

## 0. Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Пользователи | Один аккаунт. Регистрации нет, вход по паролю из переменной окружения |
| База продуктов | Собственный сид ~300 позиций + поиск в Open Food Facts как запасной вариант |
| Стек | TypeScript: React + Vite (фронт), Fastify + Prisma (бэк), PostgreSQL |
| Хостинг | Свой VPS, поддомен `fit.profkosm.ru`, HTTPS через Caddy |
| Тренировки | Логирование по подходам (вес × повторы для каждого подхода) |
| Импорт из прототипа | Не нужен, старт с нуля |

## 1. Цель и рамки

**Цель.** Одно приложение, в котором ведутся три связанных дневника — еда, тренировки, вес — и которое из этих данных считает обратную связь: реальный темп снижения веса, соответствие фактического дефицита расчётному, прогресс в силовых.

**Ключевая идея.** Приложение не просто хранит цифры, а раз в неделю сверяет «сколько ел» с «сколько сбросил» и предлагает скорректировать норму калорий.

**Вне рамок:** соцфункции, распознавание еды по фото, нативные приложения, монетизация, мультипользовательский режим.

**За основу взято:** дневник и база продуктов — MyFitnessPal / FatSecret; логирование подходов и таймер отдыха — Hevy / Strong; сглаженный тренд веса и прогноз даты — Happy Scale / Libra; таймер окна питания — Zero.

## 2. Сценарии и целевые времена

| # | Сценарий | Целевое время |
|---|---|---|

| S2 | Записать вес утром | ≤ 5 сек |
| S3 | Увидеть остаток калорий и белка на сегодня | ≤ 2 сек (главный экран) |
| S4 | Провести тренировку с логированием подходов | без ожиданий, минимум клавиатуры |

**Правило проектирования:** S1 и S2 определяют, будет ли приложение жить. Любая фича, удлиняющая S1, требует отдельного обоснования.

## 3. Функциональные требования

Приоритеты: **M** — MVP, **S** — v1, **C** — v2.

### 3.1. Аутентификация и профиль

- **FR-1.0 (M).** Вход по паролю. Хеш пароля и секрет сессии — в переменных окружения, не в БД и не в коде. Сессия — httpOnly cookie, срок 90 дней (чтобы телефон не разлогинивался). Rate limiting: 5 попыток в 15 минут по IP.
- **FR-1.1 (M).** Профиль: пол, год рождения, рост, стартовый вес, целевой вес, уровень бытовой активности.
- **FR-1.2 (M).** Расчёт нормы: BMR по Миффлину–Сан Жеору, TDEE = BMR × коэффициент активности, целевые калории = TDEE − дефицит (в % или ккал).
- **FR-1.3 (M).** Ручное переопределение любой рассчитанной цифры.
- **FR-1.4 (S).** Цель по белку в г/кг целевого веса или абсолютным числом.
- **FR-1.5 (S).** Подбюджет «сладкое / свободные калории» внутри общей нормы с отдельным индикатором.

### 3.2. Дневник питания

- **FR-2.1 (M).** Поиск по локальной базе: подстрочный, регистронезависимый, с учётом раскладки; в результатах — ккал/Б/Ж/У на 100 г.
- **FR-2.2 (M).** Добавление: продукт + количество в граммах, штуках или порциях. У продукта — список единиц с весом одной единицы.
- **FR-2.3 (M).** Записи ведутся потоком с временем; тип приёма (завтрак/обед/ужин/перекус) — опциональное поле, проставляется автоматически по времени и правится вручную.
- **FR-2.4 (M).** Редактирование, удаление, изменение времени записи.
- **FR-2.5 (M).** Свои продукты: название + КБЖУ на 100 г, сохраняются в личную базу и участвуют в поиске.
- **FR-2.6 (M).** «Недавние» и «частые»: последние 20 продуктов, добавление в один тап с тем же весом, что в прошлый раз. Главный инструмент сценария S1.
- **FR-2.7 (M).** Open Food Facts как запасной поиск: если в локальной базе меньше 3 совпадений, показать блок «нашлось в OFF». Импортированный продукт **сохраняется в локальную базу** при первом использовании, дальше работает офлайн. Обязательна пометка источника — данные OFF пользовательские и бывают неточными.
- **FR-2.8 (S).** Рецепты: блюдо из нескольких ингредиентов с указанием веса на выходе, КБЖУ пересчитываются на 100 г готового.
- **FR-2.9 (S).** Копирование дня и отдельного приёма с любой прошлой даты.
- **FR-2.10 (S).** Шаблоны приёмов: сохранить набор продуктов как «мой обычный завтрак».
- **FR-2.11 (S).** Быстрая запись без продукта: «300 ккал, 20 г белка», помечается как оценка.
- **FR-2.12 (S).** Сканер штрихкодов камерой телефона (`BarcodeDetector` с полифилом на ZXing), поиск по OFF. Требует HTTPS.
- **FR-2.13 (M).** Вода: счётчик стаканов с дневной целью.

### 3.3. Окно питания

- **FR-3.1 (S).** Настраиваемое окно (дефолт 12:00–20:00), визуальная полоса суток с отметками приёмов, текущим временем и границами окна.
- **FR-3.2 (S).** Статус: «до открытия окна X:XX» / «окно открыто, до закрытия X:XX».
- **FR-3.3 (C).** Статистика соблюдения окна за неделю и месяц.

### 3.4. Вес и замеры

- **FR-4.1 (M).** Одна запись веса на дату, повторная перезаписывает.
- **FR-4.2 (M).** Сглаженный тренд: скользящее среднее за 7 дней и экспоненциальное сглаживание (α ≈ 0.25). На главном экране показывается тренд, не сырая цифра.
- **FR-4.3 (M).** График: точки — сырые замеры, линия — тренд, пунктир — цель. Периоды 30 / 90 / 365 дней / всё время.
- **FR-4.4 (M).** Темп в кг/неделю по линейной регрессии за последние 21 день. Не считать при менее чем 4 замерах.
- **FR-4.5 (M).** Прогноз даты достижения цели при текущем темпе, с явной пометкой «экстраполяция».
- **FR-4.6 (S).** Обхваты: талия, грудь, бедро, шея. Отдельные графики.
- **FR-4.7 (S).** Фото прогресса: загрузка, привязка к дате, сравнение «до/после». Хранение на диске, не в БД; ресайз до 1600 px по длинной стороне.

### 3.5. Тренировки

- **FR-5.1 (M).** Библиотека упражнений: название, группа мышц, оборудование (штанга/гантели/резина/вес тела/кардио). Пользователь добавляет свои. Сид — упражнения под домашний инвентарь.
- **FR-5.2 (M).** Программы: именованные комплексы со списком упражнений и целевыми подходами/повторами.
- **FR-5.3 (M).** **Логирование по подходам:** для каждого подхода вес × повторы + отметка «выполнен».
- **FR-5.4 (M).** Быстрый ввод, компенсирующий трудоёмкость поподходного логирования:
  - при старте тренировки все подходы предзаполняются значениями прошлого раза для этого упражнения;
  - тап по подходу отмечает его выполненным с предзаполненными числами — клавиатура нужна, только если вес или повторы изменились;
  - кнопка «+ подход» дублирует последний;
  - шаг изменения веса и повторов — стрелки ±, не только ручной ввод.
- **FR-5.5 (S).** Таймер отдыха: запускается автоматически при отметке подхода, длительность настраивается на упражнение, сигнал вибрацией и звуком.
- **FR-5.6 (S).** История упражнения: график рабочего веса и тоннажа по датам, отметки рекордов (максимальный вес, оценка 1ПМ по Эпли).
- **FR-5.7 (S).** Недельный объём: число силовых, суммарный тоннаж, распределение по группам мышц.
- **FR-5.8 (S).** Кардио и игровые виды: тип, длительность, субъективная интенсивность 1–10, опционально пульс.
- **FR-5.9 (M).** Шаги за день — ручной ввод.
- **FR-5.10 (C).** Автоимпорт шагов из Google Fit / Health Connect.

### 3.6. Аналитика и обратная связь

- **FR-6.1 (M).** Главный экран: тренд веса, прогресс к цели, остаток калорий и белка на сегодня.
- **FR-6.2 (S).** Недельный отчёт: средние калории и белок, полнота дневника (% дней с записями), изменение тренда веса, число тренировок, средние шаги.
- **FR-6.3 (S).** **Сверка дефицита.** `TDEE_факт = средние калории за 14 дней + (изменение тренда веса за 14 дней в кг × 7700 / 14)`. Сравнение с расчётным TDEE, показ расхождения при разнице больше 10%.
- **FR-6.4 (S).** **Адаптивная коррекция.** Если темп за 3 недели вне целевого коридора (дефолт 0.5–1.0% массы тела в неделю) — предложить новую норму калорий. Приложение предлагает, не меняет само; применение в один тап.
- **FR-6.5 (S).** Рекомендация не выдаётся, если полнота дневника за период ниже 80% — иначе она построена на выдумке.
- **FR-6.6 (C).** Корреляции: шаги и тренировки против темпа снижения.

### 3.7. Напоминания

- **FR-7.1 (S).** Настраиваемые напоминания: взвешивание, приёмы пищи, закрытие окна, тренировка.
- **FR-7.2 (S).** Доставка через Web Push (VAPID) — работает при закрытом приложении; всплывающее уведомление внутри приложения — резерв. На iOS Web Push требует, чтобы PWA была добавлена на домашний экран.
- **FR-7.3 (S).** Напоминание не приходит, если действие уже выполнено.
- **FR-7.4 (C).** Telegram-бот как альтернативный канал уведомлений и быстрой записи веса сообщением. Дешевле в реализации и надёжнее пушей на iOS.

### 3.8. Данные

- **FR-8.1 (M).** Экспорт всех данных в JSON одним файлом.
- **FR-8.2 (S).** Экспорт в CSV отдельно по питанию, весу, тренировкам.
- **FR-8.3 (S).** Импорт своего JSON — восстановление в пустую инсталляцию.
- **FR-8.4 (C).** Импорт истории из MyFitnessPal / FatSecret CSV.

## 4. Нефункциональные требования

- **NFR-1. Офлайн.** PWA с service worker. Запись еды, веса и тренировки работает без сети, синхронизация — очередью операций при появлении связи. Конфликты — last-write-wins по времени изменения.
- **NFR-2. Скорость.** Первая отрисовка главного экрана ≤ 1.5 с на 4G, локальный поиск продукта ≤ 150 мс.
- **NFR-3. Мобильный интерфейс первичен.** Десктоп — адаптив. Тап-цели ≥ 44 px, числовые поля вызывают числовую клавиатуру, `autocomplete` отключён у полей поиска.
- **NFR-4. Приватность.** Данные о здоровье: никакой сторонней аналитики, никакой отправки наружу кроме запросов в OFF (только текст запроса и штрихкод, без данных пользователя).
- **NFR-5. Безопасность.** Argon2id для пароля, httpOnly + Secure + SameSite=Lax cookie, CSRF-токен на мутирующие запросы, заголовки CSP/HSTS. Загрузка фото — проверка MIME и размера, хранение вне webroot.
- **NFR-6. Бэкапы.** Ежедневный `pg_dump` по cron, хранение 30 дней локально + выгрузка на внешнее хранилище. Скрипт восстановления — в репозитории, проверка раз в квартал.
- **NFR-7. Локализация.** Русский интерфейс, метрическая система, i18n-словарь в коде.
- **NFR-8. Доступность.** Семантическая разметка, навигация с клавиатуры, контраст ≥ 4.5:1, `prefers-reduced-motion`.
- **NFR-9. Браузеры.** Последние 2 версии Chrome, Safari, Firefox. iOS Safari обязательно.

## 5. Модель данных

PostgreSQL. Однопользовательский режим, но `user_id` в таблицах сохраняется — это ноль затрат сейчас и снимает переписывание схемы, если когда-нибудь понадобится второй аккаунт.

```
users            id, password_hash, created_at
profile          user_id, sex, birth_year, height_cm, activity_level,
                 start_weight, goal_weight, kcal_target, protein_target,
                 fat_target, carb_target, sweets_budget,
                 window_start, window_end, steps_target, water_target

foods            id, user_id (null = сид), name, brand, barcode,
                 kcal_100, protein_100, fat_100, carb_100, fiber_100,
                 default_portion_g, is_sweet, source ('seed'|'own'|'off'), off_id
food_units       food_id, unit_name, grams              -- «1 яйцо» = 55 г
recipes          id, user_id, name, total_yield_g
recipe_items     recipe_id, food_id, grams

diary_entries    id, user_id, date, time, food_id?, recipe_id?, free_name?,
                 grams, kcal, protein, fat, carb,
                 meal_type, is_estimate, created_at
meal_templates   id, user_id, name, items_json

weights          user_id, date, kg                      -- PK (user_id, date)
measurements     user_id, date, waist, chest, hip, neck
photos           id, user_id, date, path, angle

exercises        id, user_id (null = сид), name, muscle_group, equipment,
                 is_cardio, rest_sec
programs         id, user_id, name
program_items    program_id, exercise_id, order, target_sets, target_reps
workouts         id, user_id, date, program_id?, note, duration_min
workout_sets     id, workout_id, exercise_id, set_index,
                 weight_kg, reps, done, created_at

activities       id, user_id, date, type, duration_min, intensity, kcal_est
daily            user_id, date, steps, water_glasses, sleep_h   -- PK (user_id, date)

reminders        id, user_id, time, kind, text, enabled
push_subs        id, user_id, endpoint, keys_json
```

Замечания к схеме:

- КБЖУ дублируются в `diary_entries` намеренно: правка продукта не должна задним числом менять историю.
- `weights` с PK по дате — одна запись в день, дубли невозможны на уровне БД.
- Индексы: `diary_entries(user_id, date)`, `workout_sets(workout_id)`, `foods` — GIN-индекс по триграммам на `name` (расширение `pg_trgm`) для быстрого нечёткого поиска.
- Продукты из OFF попадают в `foods` с `source='off'` — после первого использования доступны офлайн.

## 7. Стек и инфраструктура

### 7.1. Стек

- **Фронт:** React 18 + TypeScript + Vite, Tailwind, TanStack Query, Recharts (графики), Dexie (IndexedDB для офлайна), `vite-plugin-pwa`.
- **Бэк:** Node.js 22 LTS + Fastify + Prisma, Zod для валидации, `web-push` для пушей.
- **БД:** PostgreSQL 16 с расширением `pg_trgm`.
- **Прокси:** Caddy — автоматический Let's Encrypt, конфиг в три строки.
- **Контейнеризация:** docker compose — `app`, `db`, `caddy`.

### 7.2. Требования к VPS

| | Минимум | Комфорт |
|---|---|---|
| CPU | 1 vCPU | 2 vCPU |
| RAM | 2 ГБ + 2 ГБ swap | 4 ГБ |
| Диск | 20 ГБ NVMe/SSD | 40 ГБ NVMe |
| ОС | Ubuntu 24.04 LTS или Debian 12, x86_64 | то же |
| Сеть | любой безлимит, статический IP | то же |

Расход в покое: Postgres 150–300 МБ, Node ~200 МБ, Caddy ~20 МБ — меньше гигабайта суммарно.

Рост диска: база за год — десятки мегабайт; фото прогресса — основной источник роста (~2 МБ на снимок после ресайза); docker-образы с историей — 1.5–2 ГБ, чистятся `docker system prune`.

**Важно:** сборку фронта на сервере не делать. Vite + tsc на 2 ГБ RAM уходят в OOM. Образ собирается в GitHub Actions, на сервер приезжает готовый.

### 7.3. Первоначальная настройка сервера

1. Пользователь без root, вход по SSH-ключу, парольная аутентификация выключена.
2. `ufw`: открыты 22, 80, 443. `fail2ban` на SSH.
3. `unattended-upgrades` для security-обновлений.
4. Swap 2 ГБ (`swapfile`), `vm.swappiness=10`.
5. Docker Engine + compose plugin из официального репозитория.
6. DNS: A-запись `fit.profkosm.ru` → IP сервера. Основной домен не трогаем.

### 7.4. Caddyfile

```
fit.profkosm.ru {
    encode gzip
    reverse_proxy app:3000
    header {
        Strict-Transport-Security "max-age=31536000; includeSubDomains"
        X-Content-Type-Options "nosniff"
        Referrer-Policy "no-referrer"
    }
}
```

### 7.5. Переменные окружения

```
DATABASE_URL=postgresql://tracker:***@db:5432/tracker
AUTH_PASSWORD_HASH=$argon2id$...
SESSION_SECRET=***
VAPID_PUBLIC_KEY=  VAPID_PRIVATE_KEY=  VAPID_SUBJECT=mailto:...

```

Файл `.env` — только на сервере, в `.gitignore`. В репозитории лежит `.env.example` с пустыми значениями.

### 7.6. Деплой

GitHub Actions: сборка образа → push в GitHub Container Registry → по SSH `docker compose pull && docker compose up -d`. Миграции — `prisma migrate deploy` на старте контейнера приложения. Откат — запуск предыдущего тега образа.

## 8. Этапы

**MVP.** Вход по паролю, профиль и цели, дневник питания (локальный поиск, свои продукты, «недавние»), сид базы продуктов, вес с трендом и графиком, тренировки с поподходным логированием и предзаполнением, вода и шаги, экспорт JSON. Деплой на VPS с HTTPS.
*Готово, когда приложением можно пользоваться вместо прототипа, ничего не теряя.*

**v1.** PWA и офлайн-синхронизация, Open Food Facts, рецепты, копирование дня, окно питания, таймер отдыха, история упражнений и рекорды, недельный отчёт, сверка TDEE и адаптивная коррекция, Web Push, обхваты, фото.
*Готово, когда раз в неделю приложение само говорит, идёт план или нет.*

**v2.** Штрихкоды, Telegram-бот, импорт шагов, импорт из MFP, корреляции, PDF-отчёт.

## 9. Критерии приёмки

1. Запись типового приёма пищи из «недавних» — не более 3 тапов и 10 секунд.
2. Запись веса с главного экрана — 2 тапа.
3. Тренировка 5 упражнений × 4 подхода логируется без единого обращения к клавиатуре, если веса совпадают с прошлым разом.
4. Все данные восстанавливаются из JSON-экспорта в пустую инсталляцию без потерь.
5. При выключенной сети запись еды и веса проходит и появляется на сервере после восстановления связи.
6. График веса корректен при разрывах в данных: пропущенные дни не искажают тренд и темп.
7. Недельный отчёт на наборе за 365 дней считается менее чем за 300 мс.
8. Расчётные функции (тренд, темп, TDEE, пересчёт КБЖУ) покрыты юнит-тестами, включая граничные случаи: один замер, пустой день, нулевой темп.
9. Lighthouse PWA — установка на домашний экран работает на iOS и Android.

## Приложение A. План работы с Claude Code

Разработка ведётся агентом в терминале; ТЗ лежит в репозитории как `docs/spec.md`.

**`CLAUDE.md` в корне** фиксирует правила, чтобы не повторять их каждую сессию:
- стек и версии, структура папок (`apps/web`, `apps/api`, `packages/shared`);
- схема БД меняется только через `prisma migrate`, руками SQL не пишем;
- секреты только через `.env`, в код и в коммиты не попадают;
- каждая расчётная функция сопровождается тестом;
- ответы и коммиты — на русском.

**Порядок блоков.** Один блок — одна ветка — одна сессия. Каждый заканчивается работающим приложением.

1. Скелет монорепозитория, docker-compose, Prisma-схема, миграции, вход по паролю.
2. Сид базы продуктов и упражнений (~300 позиций, отдельный проверяемый файл).
3. Дневник питания: поиск, добавление, «недавние», свои продукты.
4. Вес: запись, тренд, темп, прогноз, график. **Расчёты — с тестами.**
5. Тренировки: программы, поподходное логирование, предзаполнение.
6. Деплой на VPS, HTTPS, бэкапы. На этом MVP закрыт.
7. Дальше — блоки v1 в порядке раздела 8.

**Что проверять самому:**
- схема БД перед первой миграцией — переделывать потом дорого;
- аутентификация и работа с cookie;
- формулы в разделе 3.6 — ошибка там тихая, цифры выглядят правдоподобно и врут.

**Что не отдавать агенту:** прямой доступ к продовому серверу и секреты. Деплой идёт через CI, `.env` живёт только на сервере.
