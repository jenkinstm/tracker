# Деплой

Сервер настраивается один раз вручную по `server-access.md`. Дальше выкатка идёт
через CI: агент и разработчик на прод не ходят (правило 6 из `CLAUDE.md`).

Прод-стек называется `tracker`, стек разработки — `tracker-dev`. Имена разные
намеренно: одинаковые заставили бы их делить тома и контейнеры, и запуск прода
подхватил бы базу разработки.

## Как устроено

```
GitHub Actions ──build──> ghcr.io/jenkinstm/tracker:<sha>
                              │
                              ▼ docker compose pull
                         сервер fit.profkosm.ru
                         ┌──────────────────────┐
                         │ caddy  :80 :443      │  TLS, сжатие, заголовки
                         │   └─> app  :3000     │  API + собранный фронт
                         │        └─> db :5432  │  postgres 16, только expose
                         └──────────────────────┘
```

Фронт **не собирается на сервере** — 2 ГБ RAM не хватит на `vite build`.
Образ собирается в CI и приезжает готовым.

Статику отдаёт тот же процесс, что и API. Caddy её не отдаёт намеренно: он не
видит содержимое образа приложения, и гонять `dist` через общий том ради
разделения — лишняя движущаяся часть. Версии фронта и бэка при таком раскладе
не могут разъехаться.

## Первая установка на сервере

Под пользователем `deploy`:

```bash
git clone <репозиторий> ~/tracker && cd ~/tracker
```

Заполнить `.env` по образцу `.env.example`. Обязательно:

| Переменная | Что это |
|---|---|
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | должны совпадать с `DATABASE_URL` |
| `AUTH_PASSWORD_HASH` | `pnpm hash-password`, argon2id |
| `SESSION_SECRET` | 32 случайных байта в base64, тот же скрипт |
| `PUBLIC_DOMAIN` | `fit.profkosm.ru` — по нему Caddy получит сертификат |
| `APP_IMAGE` | `ghcr.io/jenkinstm/tracker:latest` |

> Значения с `$` пишутся **в одинарных кавычках**: Docker Compose
> интерполирует `.env`, и argon2id-хеш без кавычек приезжает выпотрошенным.

Дальше:

```bash
docker compose -f docker-compose.prod.yml up -d
```

DNS-запись `fit.profkosm.ru` должна указывать на сервер **до** первого запуска:
Let's Encrypt проверяет домен, и без записи сертификат не выпишется.

## Доступ к образу в GHCR

Пакет остаётся приватным. Долгоживущий токен на сервере не нужен: во время
выкатки CI логинится временным `GITHUB_TOKEN`, а после перезагрузки сервера
`restart: unless-stopped` поднимает контейнер из локального кэша — `pull`
там не выполняется. `docker image prune -f` в конце выкатки чистит только
висячие слои, тег в работе не трогает.

Токен понадобится, только если образ придётся тянуть руками — например
после `docker system prune -a`. Тогда одноразово:

```bash
echo <PAT с правом read:packages> | docker login ghcr.io -u jenkinstm --password-stdin
```

## Секреты для GitHub Actions

В настройках репозитория, Secrets and variables → Actions:

| Секрет | Значение |
|---|---|
| `DEPLOY_HOST` | IP или имя сервера |
| `DEPLOY_USER` | `deploy` |
| `DEPLOY_SSH_KEY` | приватный ключ, публичная часть — в `~deploy/.ssh/authorized_keys` |
| `DEPLOY_PATH` | `/home/deploy/tracker` |

`GITHUB_TOKEN` подставляется сам.

## Что делает выкатка

`.github/workflows/deploy.yml` запускается после зелёного CI на `main` или
кнопкой. По шагам:

1. собирает образ и пушит в `ghcr.io` с тегом по SHA коммита;
2. на сервере снимает **бэкап перед выкаткой** — миграция может оказаться необратимой;
3. подтягивает образ и поднимает compose;
4. ждёт `healthcheck` до 150 секунд; если приложение не поднялось — печатает
   логи и падает с ненулевым кодом.

Миграции и сид применяются на старте контейнера, обе операции идемпотентны.

## Откат

Теги образов — по SHA коммита, поэтому откат это выбор прошлого тега:

```bash
APP_IMAGE=ghcr.io/jenkinstm/tracker:<прошлый-sha> \
  docker compose -f docker-compose.prod.yml up -d app
```

Если ломалась миграция — сначала восстановить базу из дампа, снятого перед
выкаткой (`scripts/restore.sh`), и только потом откатывать образ.

## Бэкапы (NFR-6)

`scripts/backup.sh` снимает `pg_dump`, сжимает, кладёт в `./backups` и удаляет
дампы старше `RETENTION_DAYS` (по умолчанию 30). Пустой дамп считается отказом:
молча положить нолик в бэкапы хуже, чем упасть.

Cron под пользователем `deploy`:

```
0 4 * * * cd /home/deploy/tracker && ./scripts/backup.sh >> backups/backup.log 2>&1
```

Копия наружу — через `rclone`, если задан `BACKUP_REMOTE`. Диск сервера не
бэкап, если сервер и есть точка отказа.

Восстановление:

```bash
./scripts/restore.sh backups/tracker-2026-07-28_0400.sql.gz
```

Скрипт останавливает приложение, заливает дамп и поднимает обратно. Операция
разрушающая, спрашивает подтверждение.

**Раз в квартал проверять восстановление** — этого требует NFR-6. Проверять
лучше не на проде: поднять `docker-compose.prod.yml` на другой машине с пустым
томом и залить туда дамп.

## Экспорт данных как второй контур

`pg_dump` спасает от потери сервера, но привязан к версии Postgres и схеме.
Экспорт JSON (`/api/export`, экран «Данные») читается чем угодно и переживает
смену схемы. Второй контур стоит скачивать руками хотя бы раз в месяц.

Проверка восстановления из JSON — критерий приёмки №4:

```bash
docker compose run --rm api pnpm backup:check
```
