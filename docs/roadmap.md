# Порядок работ

Один блок — одна ветка — одна сессия. Каждый блок заканчивается работающим
приложением, а не половиной модуля. Отмечай сделанное здесь.

## MVP

- [x] **Блок 1. Скелет.** Монорепозиторий (`apps/web`, `apps/api`, `packages/shared`),
      docker-compose для локальной разработки, Prisma-схема из раздела 5 ТЗ,
      первая миграция, вход по паролю (FR-1.0), пустой главный экран.
      *Проверка: `docker compose up`, вход по паролю, сессия держится после перезагрузки.*

      Отклонения от раздела 5 ТЗ, принятые при проектировании схемы:
      `users.password_hash` убран (хеш в `.env`, ТЗ противоречило само себе);
      `diary_entries.free_name` → `name` как снимок названия + денормализованный
      `is_sweet`; `updated_at` во всех изменяемых таблицах и строковые `cuid()`
      вместо автоинкремента — под офлайн-синхронизацию (NFR-1); время суток
      хранится как `VARCHAR(5)` «ЧЧ:ММ»; КБЖУ и вес — `Float`.

- [x] **Блок 2. Сиды.** 313 продуктов, 54 упражнения и три программы A/B/C.
      Отдельные файлы данных, которые можно вычитать глазами, а не генерация в коде.
      *Проверка: поиск по базе находит «гречка», «творог», «куриная грудка» с адекватными КБЖУ.*

      Данные лежат в `apps/api/src/seed/` (не в `prisma/`: корневой vitest
      собирает тесты только из `src/`). Заливка идемпотентна за счёт
      детерминированных id `seed:<slug>` вместо `cuid()` — миграция не
      понадобилась. Сид гоняется на старте контейнера `api`.

      Конвенция по данным: КБЖУ на 100 г готового продукта, углеводы **общие**,
      клетчатка входит в них (USDA, а не маркировка по ТР ТС). Проверяется
      тестами: ккал против макросов по Этуотеру, дубли, границы.

- [x] **Блок 3. Профиль и цели.** FR-1.1 – FR-1.5, расчёт BMR/TDEE с тестами.
      *Проверка: цифры совпадают с ручным расчётом по формулам из context.md.*

      Расчёты — `packages/shared/src/nutrition.ts`, 45 тестов. Миграция
      `profile_targets`: режим и величина дефицита (FR-1.2), белок и жир
      на кг целевого веса (FR-1.4).

      Решения, принятые при проектировании:
      BMR считается от **последнего взвешивания**, при его отсутствии — от
      стартового веса; источник возвращается в API и показывается в интерфейсе.
      Каждая цифра считается независимо и может остаться `null` — белок и жир
      не зависят от пола и возраста, прятать их за незаполненным годом рождения
      незачем. Углеводы в `effective` пересчитываются от переопределённых
      калорий, иначе сумма макросов разошлась бы с нормой. Норма не опускается
      ниже `MIN_TARGET_KCAL` = 1200. `context.md` даёт только мужскую формулу
      Миффлина — женская (−161) добавлена, иначе поле `sex` неработающее.

      Дефолты профиля из `context.md` проставляет сидер, **только в пустые
      поля**. Пола и года рождения в них нет намеренно: без них приложение
      честно показывает «заполни профиль», а не норму от выдуманного возраста.

- [ ] **Блок 4. Дневник питания.** FR-2.1 – FR-2.6, FR-2.13. Поиск, добавление,
      редактирование, «недавние», свои продукты, вода.
      *Проверка: критерий приёмки №1 — приём пищи из «недавних» за 3 тапа.*

- [ ] **Блок 5. Вес.** FR-4.1 – FR-4.5. Запись, тренд, темп, прогноз, график.
      **Все расчёты — с тестами**, включая разрывы в данных.
      *Проверка: критерии приёмки №2 и №6.*

- [ ] **Блок 6. Тренировки.** FR-5.1 – FR-5.4, FR-5.9. Программы, поподходное
      логирование, предзаполнение прошлыми значениями.
      *Проверка: критерий приёмки №3 — тренировка логируется без клавиатуры.*

- [ ] **Блок 7. Экспорт и деплой.** FR-8.1, docker-compose для прода, Caddy,
      GitHub Actions, бэкапы, HTTPS на `fit.profkosm.ru`.
      *Проверка: критерий приёмки №4 — восстановление из JSON в пустую инсталляцию.*

**После блока 7 MVP закрыт** — приложением можно пользоваться каждый день.
